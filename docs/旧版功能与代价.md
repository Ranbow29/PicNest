# 旧版 PicNest（Electron）功能实现与代价盘点

> 材料来源：旧版 `PLAN.md` / `HANDOFF.md` / `PLUGIN.md` / `MOTION.md` / `HANDOFF-GEMINI.md` / `HANDOFF-PINTEREST.md` / `HANDOFF-VISUAL-SEARCH.md`
> 目的：在重写 Rust 版时，看清每个功能**怎么实现的、代价在哪**，避免只抄效果不抄代价。
> 记录：2026-11-14

---

## 0. 一句话总结旧版架构

**直链索引**：SQLite 只存 `file_path` + 元数据，图片原地不动；物理文件夹是真源，层级从路径派生。
所有"库的能力"（排序、评分、标签、回收站）都是**在数据库和元数据文件上打补丁**，唯一会碰磁盘的是「物理排序」和「删除文件夹」。

---

## 1. 功能 → 实现 → 代价

### 1.1 索引与元数据

| 功能 | 旧版实现 | 代价 |
|---|---|---|
| 直链索引 | `images` 行只记 `file_path`，不复制文件 | 文件一旦在外部被移动/改名，索引即失效，必须有同步机制 |
| 根元数据 | `.picnest/meta.json`（点目录，`attrib +h` 隐藏），存标签/评分/注释/URL/收藏/文件夹颜色/手动排序 | 单文件约 **774KB**（10764 图）；每次改动重写整个文件；外部同时改时"最后写入者赢"，无合并 |
| 目录顺序 | `picnest_dir_order`，键 `<folderId>|<rel>`；旧全局键启动时复制到各库 | 键的生成规则（大小写、`__root__` vs 空）极易出错，错了就静默失效 |
| 图片顺序 | `images.sort_order`；`0` = 新录入，排最前 | 无 |

### 1.2 缩略图（三级）

| 层级 | 旧版实现 | 代价 |
|---|---|---|
| 400px 缩略图 | sharp 生成，缓存 `md5(file_path)` | 每张一次解码+缩放；磁盘占用 |
| 1024px 显示图 | 网格大格用，`md5(path|d1024|mtime)` | 多一级缓存文件 |
| 2048px 视口预览 | 灯箱/简报缩放用 | 再多一级 |
| 缓存目录 | `dataDir/picnest-thumbs` | **不能叫 `cache`**：与 Chromium 自己的 `Cache` 同名（大小写不敏感），浏览器清缓存会把缩略图一起清掉（实测 340MB 只剩 `Cache_Data`） |

**关键设计**：网格**不直接解码原图**。>500px 大格原图可能 10MB+，Chromium 的 decoded-image 预算约 128MB，多张并行就 `EncodingError` / 裂图。

### 1.3 排序与文件名（旧版最复杂的一块）

| 功能 | 旧版实现 | 代价 |
|---|---|---|
| 手动排序 | 拖动换位写 `sort_order`；`sort_order=0` 置顶 | 仅手动模式可拖（防止覆盖） |
| 应用为手动排序 | 把当前显示顺序批量写入，可**真实改名**为 `01_原名` | 批量改名，先弹确认 |
| **物理排序开关** | 两阶段改名（临时名避免互换撞名）→ 暂停 watcher → 同步 DB 路径/缩略图缓存/dirMemory 键/dirOrder 嵌套键/回收站 abs_path → 重开 watcher | ⚠️ **无撤销、无预览**；开启后每拖一次就全量重命名；改名前不确认；权限不足的目录只记错误不回滚；极端情况残留 `__pn_tmp_*`；**旧版没有迁移缩略图缓存到新哈希的意识 → Rust 版照抄时直接把整库缩略图清空了** |
| 隐藏排序编号 | 顶栏 `01`，纯显示层剥离，正则 `^(?:\d{1,3}|0\d{3})_+` | 只影响显示；改名时要把前缀接回去，否则一次改名打乱物理排序 |
| 清除排序编号 | 扫描整个根，**先子后父**，重名自动 `(2)`，跳过点目录 | 批量改名，危险操作，需确认 |

### 1.4 回收站（这里就是"内部回收站"）

| 对象 | 旧版实现 | 代价 |
|---|---|---|
| 图片 | 纯软删：`deleted_at` 打标记，**文件原地不动** | 磁盘空间不释放；用户容易误解"删了还在" |
| **文件夹** | **真移动到 `AppData\Roaming\PicNest\picnest-trash\<rootId>\<id>-<name>`**，行记 `deleted_at + trash_group` | 这就是旧版的"内部回收站"：占磁盘、需要维护 `abs_path`/`trash_path` 两套路径；彻底删除时才进 Windows 回收站 |
| 同步时 | `removed` 必须跳过 `deleted_at` 非空行（P8a–P8d） | 否则回收站还原会丢图 |

### 1.5 查重

| 层级 | 旧版实现 | 代价 |
|---|---|---|
| 精确 | 按 `size` 分桶（只对同尺寸读盘）→ 流式 MD5（并发 4） | CPU + 随机读；全库 6724 文件 258ms |
| AI 视觉 | dHash → 32×32 色块 + pHash 预筛 → 候选对缩略图发视觉 API 判 `{same}` | 网络 + 费用（约 340 tok/对）；只上传 384px 缩略图；必须显式勾选允许上传 |
| 实时性 | 无后台定时扫描 | 需要手动触发 |

预筛效果实测：3372 张 → dHash 4145 对 → 色块+pHash 筛掉 97.5% → 104 对进 AI。

### 1.6 采集（浏览器扩展）

| 部分 | 旧版实现 | 代价 |
|---|---|---|
| 扩展 | 自研 MV3；右键存图/截图、网页内按住 380ms 出双栏面板拖放 | 维护成本极高：Pinterest 的 `pointer-events:none`、`setPointerCapture`、bfcache、`document.open()` 都会干掉注入脚本；版本迭代到 v0.1.5 才稳定 |

| 未做 | token 鉴权、整页滚动截图、视频、跨域 iframe | — |

### 1.7 大图 / 简报 / 文本 / 视频

| 功能 | 旧版实现 | 代价 |
|---|---|---|
| Canvas 舞台 | 整窗 canvas + DPR，只 `drawImage` 可视源矩形；preview 先载、full 懒载 | 复杂；超大图 first full 解码仍有成本；未做多级 tile cache |

| 文本缩略图 | 前 26 行 → 800×1040 SVG 纸面 → webp | sharp 生成 |
| 文本编辑 | 自动识别编码、保留 CRLF、1.5s 自动保存 | >2MB 只读 |

### 1.9 Eagle 迁移

物化文件夹树（Eagle 把文件平铺在 `images/<id>.info/`，直接索引会丢层级）；本次迁移 11,365 条 / 18.25GB；预置 8654 张 Eagle 缩略图。
代价：**全量复制**（18GB）、元数据一次导入无增量、多文件夹条目会重复落文件。

### 1.10 插件系统（PLUGIN.md）

| 类型 | 运行环境 | 能力 | 风险 | 状态 |
|---|---|---|---|---|
| `theme` | 渲染层直接注入 CSS | 只改设计 token（颜色/圆角/动效参数） | 低（无代码执行） | 已实现 P1 |
| `renderer` | `iframe sandbox="allow-scripts"` + postMessage RPC | UI 插槽、事件订阅、只读查询、插件私有 KV | 中（无 Node、无宿主 DOM） | 已实现 P2 |
| `main` | `utilityProcess` 独立进程 | 宿主代理过的 fs/db/网络 | 高（必须过权限网关） | **未做 P3** |

**已做**：theme + renderer 沙箱 + 插件库 UI（已安装/仓库页签、文件夹安装、registry zip + sha256、启停卸载）。
**未做**：main 插件、签名校验、`ui.contextMenu` 插槽、多文件资源（renderer 只允许单文件 HTML，资源走 data URL）、默认在线 registry。

**机制细节**：权限 `deny by default`，未声明即拒；升级新增权限要重新确认否则保持禁用；主题插件只允许叠 CSS token（不允许整页覆盖）；插件网络走宿主代理，只放行声明 origin；插件私有存储 `host-storage.json`，宿主统一管并发与 **5MB 配额**；`onDispose` 超时 3s 强拔 DOM；main 插件内存 >256MB 或 CPU 持续 >80% 达 10s 则 kill。

**代价**：
- 三套运行环境各自维护，沙箱边界（同源、Node、宿主 DOM 三样都得封）设计成本高
- 插件资源只能单文件 HTML，多资源要内联成 data URL（base64 肤胀内存）
- 不提供 db 句柄，能力要一件件做成 RPC；`picnest-plugin-query-*` 相当于复制出一条查询路径，两处 SQL 要同步演进
- 事件投递要侵入既有 store action（`emitPluginEvent`），事件语义一变就波及插件
- **无签名校验**，靠 sha256 + 人工 PR 审核兜底

### 1.11 以图找图（VISUAL-SEARCH.md）
| 项 | 实现 |
|---|---|
| 引擎 | **单 Pinterest Lens**（最初设计过“Pinterest + 花瓣”双引擎，后砍成单引擎；花瓣适配器已不维护） |
| 三栏布局 | 任务队列（~60px 缩略图列）/ ROI 框选（4 角 4 边手柄，350ms 防抖重检索）/ 瀑布流结果（列宽 120–360px） |
| 快捷键 | `F` 把在线图压入队列递归搜索、`S` 无损下载入库到当前文件夹、`O` 打开原网页 |
| 网络层 | 主进程适配层（`picnest-visual-search.js`），带 token 鉴权 |
| 登录态 | `session.fromPartition('persist:pinterest')` 持久会话，401/403 时弹内嵌 webview 登录一次 |

**代价（这部分最重）**：
- **原图会离开本机**：Pinterest Lens 要先流式上传本地图换临时上传标识
- **完全依赖 Pinterest 的非公开接口与反爬策略**，随时失效；v0.1.0 封版就在修右键菜单穿透、Edge 的 token 非 ISO-8859-1 崩溃
- 登录态落盘（`persist:pinterest` 分区），风控/失效即整条链路不可用
- ROI 改选 350ms 防抖只推迟、不合并 → 外部请求量放大
- 递归搜索（F 键）**没有深度限制**，队列和请求会无限膨胀
- 批量入队 = 批量上传
- 单引擎后：不再有“两家结果交错”的复杂度，但也没有备选方案，Pinterest 一挂功能全挂

## 2. 代价汇总（按资源归类）

| 资源 | 消耗点 | 量级 |
|---|---|---|
| **磁盘** | 三级缩略图缓存 + 内部回收站（整文件夹）+ Eagle 迁移副本 + 根元数据 774KB | 缩略图数百 MB；回收站等于被删文件夹大小；迁移 18GB |

## 3. 旧版用血换来的纪律（值得直接继承）

1. **缩略图缓存目录不能叫 `cache`**（与 Chromium Cache 撞名会被清空）。
2. **改名必须同步五处**：DB 路径、缩略图缓存名、dirMemory 键、dirOrder 嵌套键、回收站 `abs_path`。少一处就是静默损坏。
3. **sync/scan 的 removed 必须跳过 `deleted_at` 非空行**，否则回收站还原丢图。
4. **手动排序保护**：非 `manual` 模式不允许拖动写 `sort_order`。
5. **增量优先**：排序/移动不整表 `loadImages`，否则选中态、滚动位置、入场波全乱。
6. **物理交互只有用户的鼠标是真相**，CDP 合成拖拽只能证明分支，不能证明手感。
7. 文件名前缀正则只认 `1–3 位` 或 `0` 开头的 4 位，避免把 `2026_08_23` 这类日期当编号。

## 5. 下一步可以先想的几件事

1. **三级缩略图要不要补**：Rust 版只有 400px，大格显示原图会重现旧版“解码预算爆掉裂图”的问题。这是**效果差距最大的地方**。
2. **目录删除的语义**：旧版有内部回收站（`picnest-trash/<rootId>/<id>-<name>`，可还原文件夹），Rust 版直接进 Windows 系统回收站。要统一得补 `picnest-trash` 目录 + `trash_group` 维护。
3. **采集服务**：旧版 41600 是独立一条产品线（扩展 + 服务端），Rust 版完全没有。
4. **以图找图**：完全没做，且旧版本身也是个“靠网页结构吃饭”的脆弱功能。
5. **Canvas 舞台**：大图/简报高倍平移的流畅度差距来源。
6. **插件系统**：要做得先把沙箱边界和权限清单想清楚，不是小活。

## 6. 关于“实时同步文件名”（Feb 的判断 + 实现现状）

**Feb 的判断（我认同）**：
- 修改本身就是每次修改后变一次；编号已存在时，只有“夹在修改位置中间”的文件换号
- 同一批文件反复改名，OneDrive 最终只落最后一次状态
- 开关不勾就完全不发生，对不需要的人零影响
- 实时比手动省操作

**为什么成立**：实现是“只改编号与实际位置不符的”。顺序没变时实测 `changed = 0`（点两次都不动文件）。

**体验代价已解决**：自动改名后**不整表重载**，用后端返回的 `map`（old → new + 新缩略图）在本地替换 `images` 字段。实测：拖拽后顺序立即变、自动改名后只换编号，**选中态和缩略图全程不丢**。

**同时修了一个隐形冲突**：改名动作本身会产生大量文件事件，watcher 随即 `loadImages`，把刚写好的顺序又盖回去（实测导致文件名顺序错乱）。现在内部操作（拖拽、自动改名）期间会设 `_suppressFsSyncUntil` 抑制 watcher 回写——这正是旧版纪律里“内部操作设 suppress 时间戳”那条。

**仍然存在的特性**：编号是 1..N 连续的，插入一张会让中间几张顺移。想要“只动一两个”就得换稀疏编号（10/20/30，插入用 15），代价是编号不连续、看着跳号。
