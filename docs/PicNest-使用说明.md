# PicNest 图巢 · 使用与行为说明

> 记录时间：2026-11-14 · 对应版本：`PicNest.exe`（Tauri/Rust 版）
> 这份是**给你看的**：每个操作到底做了什么、会不会动磁盘、有哪些坑。
> 技术细节另见 `docs/BEHAVIOR.md`。

---

## 一句话模型

**图巢 = 数据库索引 + 磁盘原文件。它不复制图片，只记路径、尺寸、评分、标签、排序。**

所以有两套"真相"：

| | 更新时间 | 谁说了算 |
|---|---|---|
| **文件夹结构** | 实时（每次刷新都读磁盘） | 磁盘 |
| **图片列表 / 顺序** | 要同步才更新 | 数据库 |

新建一个文件夹立刻就能看见（读磁盘）；往文件夹里丢一张图，要等同步才知道（读数据库）。

---

## 各操作的准确行为

| 操作 | 磁盘上发生了什么 | 数据库里发生了什么 |
|---|---|---|
| 新建文件夹 | **真的建目录** | 无（下次刷新读磁盘就有） |
| 拖入/粘贴图片 | **真的复制文件** | 自动入库（文件监听） |
| **删除图片** | ⚠️ **什么都不发生，文件原地还在** | 打 `deleted_at` 标记，进回收站视图 |
| 删除文件夹 | **移进 Windows 系统回收站** | 打标记 |
| 拖拽排序 | 不动 | 写 `sort_order`；开关开启时 800ms 后自动写文件名 |
| 同步到文件名 | **真的改文件名**（加 `001_` 前缀） | 更新路径 + 迁移缩略图缓存 |
| 导出 | 复制一份到目标目录 | 不动 |

**最容易误解的一条**：图巢里"删除图片"只是**隐藏**，文件还在磁盘上。想真删得在资源管理器里删，或者用回收站的"彻底删除"。

---

## 关于"内部回收站"

**没有。** 库里只有一个 `.picnest/meta.json`（存库的元数据：封面、颜色、目录记忆），没有专门的回收站目录。

三种"删"要分清：

| 说法 | 实际 |
|---|---|
| 图巢删图片 | 只打标记，文件不动 |
| 图巢删文件夹 | 移进 **Windows 系统回收站**（能在资源管理器回收站里找到） |
| 回收站里"彻底删除" | 真删文件 |
| 在资源管理器里删 | 文件监听会把这些行也标记进图巢回收站 |

---

## 三个"方向"别混

**① 磁盘 → 库（入库）**
- **全自动**：切进目录 1.2 秒后扫一次；文件监听负责新增/删除/改名
- 没有手动入口（旧版那个「从磁盘重新读取」按钮已删，因为监听已经盖住）
- 行为：新文件入库；磁盘上没了的标记进图巢回收站

**② 库 → 磁盘（落地排序）**
- **全自动**：右键勾上「✓ 排序同步文件名」后，拖完顺序 800ms 自动写当前这一层
- 开关会记住（`localStorage`），不用每次勾
- 行为：按库里顺序给文件名加 `001_` 前缀；**只改名字，不动内容**；缩略图缓存跟着迁移；选中和滚动不会被打断

**③ 导出**
- 「导出（含子文件夹）」保留原名
- 「导出（去掉数字前缀）」副本去掉 `001_`，原库不动

---

## 排序三层

```
图片顺序   →  images.sort_order        ← 你拖出来的，存在库里
目录顺序   →  picnest_dir_order       ← 左栏拖动，存在库里
文件名前缀 →  磁盘上的 001_xxx.jpg     ← 上面两者的"投影"
```

**前两层是主，第三层是投影。** 同步做完三者一致；之后只有显式同步才会再对齐。

几个必然现象，不是 bug：

- 点「标题」排序看不出变化 → 已经同步过，两者一致
- 移动一张图会改好几个文件名 → 编号是 1..N 连续的，插入会让中间几张顺移
- 「标题」模式下拖不动 → 有意为之，防止覆盖手动排序

---

## 顶栏那个 `01` 按钮

控制**界面上是否隐藏** `001_` 这类前缀。磁盘名不变，只是看得见看不见。

- 开着（默认）：界面显示干净的名字
- 关掉：界面显示真实文件名（带编号）

---

## 缩略图

- 400px、JPEG q80，一张约 28KB，存在 `%LOCALAPPDATA%\PicNest\cache\thumbs`
- **缓存是按"文件完整路径"算哈希命名的**
- 所以任何改名都必须迁移缓存——否则那张图变灰卡（PSD 尤其明显，因为它要重新解析内嵌预览）

---

## 已知限制

1. 文件名前缀只认 **2–3 位数字 + 下划线**；`0524_`、`2023_` 这种日期开头不碰。
2. 改名后 OneDrive 会重新同步这些文件（元数据变更，会忙一阵）。
3. 导出没有"只导出选中"。
4. 非手动排序模式下不能拖动换位。
5. 边拷图边让自动同步触发，新拷进来的可能不进本次改名计划。等拷完再挪一下顺序。
6. 文件监听不分场合：你在资源管理器里的任何增删改名、OneDrive 的云端变更，都会触发图巢同步。

## 这一轮改了什么

- 缩略图从无损 webp（167KB）换成 JPEG q80（28KB），解码快一倍
- 取数改走本地 HTTP，不再走会堵的 IPC
- 切目录不再让树上 60 多个图标同时重播动画（那是"点了要等一秒"的元凶）
- 同步目录的查询改走索引，784 张的目录从 20–32ms 降到 1ms
- 拆掉旧的「物理排序」三个命令（它会清空整库缩略图）
- 重做「排序同步文件名」：默认关、拖停 800ms 才跑、只改当前层、缓存迁移
- 恢复顶栏 `01` 隐藏按钮；重命名时保留排序前缀
- 导出新增「去掉数字前缀」
- 新建文件夹合并成一个（建在右键的文件夹里）
- 补上文件监听（自动入库 + 自动处理删除）
- 清理了 33 条孤儿记录，恢复目录顺序
